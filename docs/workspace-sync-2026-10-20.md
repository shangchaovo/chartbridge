# 三端配置双向同步，首次从 MacBook 导入（2026-10-20）

## 首次启用

用户指定首次以 MacBook 的映射终端现有配置为基准，并进一步确认：此后所有终端平等，任何一端的修改都覆盖同步到其他终端。Windows 服务对外提供同一套资源，项目的 Mac 启动脚本使用 Windows 隧道；只读 SSH 检查也确认 Mac mini 的 18765 端口由 `local.shanhai.windows-tunnel` 转发至 Windows，而非另一份独立服务。

配置同步功能已部署到当前主机。顶部新增固定可见的文字按钮「多端同步」，390px 窄屏也可以直接访问；图表设置按钮增加文字，专门同步窗口还提供「打开图表设置」。原有颜色、收藏等数据在 MacBook 浏览器里，首次通过 **MacBook 映射页面刷新 → 多端同步 → 首次从此终端导入配置** 发布。其他终端首次更新前端也需要刷新一次。此后无需手动导入导出或重复点同步。也支持 `?settings=sync` 直接打开同步窗口。

首次导入前，服务维持未初始化状态，保留各终端原有偏好。首次导入只执行一次，来源标识保留为历史信息；所有终端随后都通过同一个配置修改接口编辑，不依据来源设备决定优先级。

## 持久化与冲突

`WorkspaceStore` 在现有 SQLite 表中增加 `settings` 记录。工作区字段、偏好、首次导入来源和版本号在同一事务内提交；提交后通过 `/api/workspace-sync/events` 推送。重连发送最新快照，页面恢复可见或网络上线时补读一次。

客户端只发送实际改动的字段和通过控件主动改动的偏好。旧缓存或旧页面的原生 localStorage 写入不能自动变成待发布偏好。尚未发送的修改写入当前浏览器的草稿；其他终端首次接受 MacBook 配置时也会备份原配置。

不同项目的修改分别保留，同一项由服务器最后收到并成功保存的修改覆盖，包括自选列表。离线主动修改在恢复网络后提交，按同一保存顺序参与同步。MacBook、Windows 与其他 Mac 都使用相同规则。旧前端仍调用 `/api/state` 整份保存时，服务保留已经初始化的共享配置。

客户端以编辑序号区分保存中的操作和后续操作，收到较晚的旧响应时只确认该请求实际保存的编辑；较新的 SSE 版本不会被旧回执反向覆盖。每次请求使用固定批次 ID，服务在 `workspace_settings_batches` 表中把回执与设置事务一起保存。网络结果不确定时重试原批次；已经提交的批次只返回最新状态，不能再次覆盖其他终端后来保存的值。回执和未确认请求在服务重启及浏览器草稿恢复后仍有效。

面板尺寸和工具栏位置保留共享目标值，各终端仅约束实际显示，不在窗口缩小时反向覆盖配置。

## 同步时效优化(同日第二轮)

用户反馈「同步不够及时」。实测定位四个延迟来源并全部修复:

1. **画线通道防抖无上限**(`src/collaboration.js`):650ms 防抖在连续操作(拖动连线、连续画图)时每次落笔都重置,flush 可能被无限推迟。改为 200ms 防抖 + 800ms 最大等待上限(从首个未保存编辑起算),连续编辑期间也保证至少每 800ms 发布一次。保存进行中收到的编辑在保存落定后立即重发,不再重新排队等一轮防抖。
2. **设置通道同样的无上限问题**(`src/workspace-sync.js`):180ms 防抖改为 120ms + 500ms 最大等待上限;保存落定后有积压编辑时立即重发,替代原 1500ms 固定等待。失败重试仍保持 1500ms 退避。
3. **SSE 重连不补拉**(`src/collaboration.js`):图表通道重连成功后原来只更新状态,断线期间的画线/视图修改要等本端下一次操作才能收到。现在重连(`onopen`)立即补拉一次房间快照。
4. **切回标签页不刷新画线**(`src/main.js`):visibilitychange 恢复时原来只刷新设置通道,现在同时补拉共享图表快照。

服务端补上一个现有隐患:`/api/chart/events` 端点原来先取快照再订阅变更,两步之间的提交会漏推(仅靠客户端补拉兜底)。改为先订阅再取快照。

实测(单机回环,真实类实现):设置端到端 138ms;画线单次编辑 217ms(旧版 650ms);8 连击突发稳定在 ~800ms 封顶(旧版无上限)。测量脚本保留在 `work/sync-latency-baseline-20261020.mjs`。

新增 6 项时序回归测试(突发上限、竞态立即重发、重连补拉)。全量自动测试 251 项通过、0 失败。多智能体对抗审查确认:服务器每批次恰好产生一次 SSE 推送、无服务器端延迟;`racing` 标志泄漏与 50ms 轮询无上限两个隐患也已在本轮修复。

## 26 代理对抗审查结论(同日)

对上述优化跑了一轮 26 代理的审查 + 对抗验证(22 项发现,13 项被驳回,9 项被确认为真实)。处置结果:

| 确认的问题 | 处置 |
|---|---|
| `racing` 标志泄漏 → 后续 flush 全部 0ms(no-burst 保护失效) | 修复:finally 无条件采集并清除 |

| 突发测试在事件循环卡顿时可能误报 | 修复:放宽断言余量至 500ms,保持对旧实现(无上限)的甄别力 |
| 画线通道与 PUT /api/state 双写 drawings,两个.sqlite 各存一份,重启按旧副本重建房间 | 场景重演确认(正是上次锁定修复的根因);本轮已把两个存储重新对齐(房间 rev 15706),并把该行为记录为已知设计边界。根治需要一段"协作房间主存 drawings 后 PUT 剥离"的改动,牵动旧页面兼容,未并入本轮 |
| setField PATCH 无乐观并发检查,陈旧 baseRevision 不报 409 | 设计语义(文档声明 last-writer-wins),非缺陷 |
| 服务端 SSE 每批次即时推送,无服务器端延迟 | 结论性确认:瓶颈全在客户端防抖,本轮优化命中要害 |
