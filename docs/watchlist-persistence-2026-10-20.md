# 自选持久化修复与恢复（2026-10-20）

## 原因

本机 `work/server.log` 中存在多次 `/api/state` 保存失败：Windows 返回 `EPERM`，拒绝把写好的 `workspace.json.<uuid>.tmp` 替换为 `workspace.json`。启动时只读取旧文件，因此新添加的品种在重新进入后消失。

原保存还有 800ms 延迟，添加后立即刷新或关闭可能早于落盘；从搜索结果切换新品种时，如果行情加载失败，也不会执行成功分支中的自动保存。另一个问题是旧标签页会把过期的完整自选数组写回，覆盖其他标签页的新修改。

## 修复

- 主机工作区使用 `data/workspace.sqlite`，由 SQLite 事务一起提交当前和上一个版本，启用 WAL 与 `synchronous=FULL`。写入成功才返回保存成功，工作区保存不再依赖替换 JSON 文件。
- 首次启动自动迁移旧 `workspace.json`，若旧文件损坏则尝试 `workspace.previous.json`。迁移后以数据库为准，旧 JSON 保留为迁移来源。工作区的导入、导出界面仍使用 JSON。行情、提醒后台任务和本机自选导入统一读取当前工作区存储。
- 自选增删和排序立即写入当前浏览器的 `shanhai-watchlist`，包含待保存标记及修改前的列表。重新进入时，未落盘修改与主机最新列表合并并重试保存。
- 局域网个人自选仍保存在各自浏览器中，重新输入连接凭据后恢复；只读访问不会取得主机的个人工作区。其他工作区设置损坏时，单独有效的自选备份仍可恢复。
- 保存请求携带列表修改前的基准。未修改列表的旧标签页不会覆盖服务器新内容；增删和排序按基准合并。旧版页面未携带基准时，保存会保留当前列表中缺失的品种，防止更新过渡期间再次清空自选。
- 搜索选择新品种和导入配置时，保存不再依赖行情请求成功。浏览器的工作区请求按顺序提交。
