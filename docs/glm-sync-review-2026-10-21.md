# GLM 同步改动审查与修正

日期：2026-10-21。用户提供 GLM 操作转录，要求继续完成需求并审查。审查依据是当前源代码、可重复失败的回归测试及隔离服务 HTTP/SSE 验收，不以转录中代理数量或测试总数作为正确性依据。

保留 GLM 的有效改进：图表通道 200ms 防抖与 800ms 连续编辑上限，设置通道 120ms 防抖与 500ms 上限，图表 SSE 重连补拉，以及恢复前台时刷新两条通道。这些是客户端调度参数，跨设备的实际耗时还取决于网络、请求执行和浏览器后台调度。

## 确认的问题

| 优先级 | 问题与复现 | 修正 |
|---|---|---|
| P1 | `WorkspaceSync.flush` 失败时，`pending` 仍包含正在重试的编辑。因此 `retryBatch && !pending.size ? retryMs : 0` 在普通断网场景下选择 0ms，形成快速重试循环。回归测试中，第一次失败后仅推进 1ms 即出现第二个请求。 | 用独立重试时间记录退避；网络结果不确定时保留原批次和幂等 ID，后续设置变化或 SSE 不缩短退避。成功保存后积压编辑仍立即发送。 |
| P1 | 保存矩形 110 的请求尚未返回时，本地再次改为 120；收到自己的 110 保存回执，被三方合并误判为另一终端改动，产生 `drawings/BTCUSDT\|1d/rect` 冲突并停止同步。原时序测试只测试了不同字段，未覆盖同一图形。 | 将自己提交的确切操作作为回执合并的基准。HTTP 回执和先到达的自有 SSE 均可识别；超过 100 项时只确认本批实际提交的操作，未发送的编辑保留。 |
| P2 | 设置返回带当前版本的 409 后，旧 `retryBatch` 未丢弃，下一次仍发送旧版本及旧批次。 | 明确未提交的 409 使用新快照重建批次；网络结果不确定时才重试原批次。 |
| P2 | 图表客户端在请求进行中关闭，失败回执的 `finally` 会重新创建重试计时器。新增的 50ms 轮询也增加了不必要的计时任务。 | 增加关闭状态，阻止关闭后的应用、发布和定时重试；直接复用进行中的请求，并在完成时处理积压编辑，移除轮询。设置客户端关闭后也不再从迟到回执改写草稿。 |
| P1，既有一致性缺口 | 工作区读取和整份 PUT 使用工作区副本，图形编辑却使用协作房间；两处曾出现不同锁定/坐标。一次手动合并没有阻止旧整份保存再次写入不同副本。 | 工作区绑定协作房间作为图表数据源：读取即时投射房间字段；保存个人配置时保留房间中的图形、坐标、锁定、批注及其他图表字段。图形修改仍走带版本检查的协作接口。 |

## 存储和兼容范围

`charts.sqlite` 的主协作房间是图表主数据；`workspace.sqlite` 继续保存主题、自选、提醒等工作区配置。旧客户端的 `/api/state` PUT 可以保存个人配置，但其中携带的过时图表字段不能替换房间数据。工作区读取会投射房间当前状态，不要求两个数据库的原始 JSON 始终逐字节相同。

现有协作房间在正常重启时会继续读取已存在的房间记录，不会每次都用 workspace 重新播种；旧工作区仅用于首次创建缺失房间时的初始化。这一点也更正了先前转录对重启行为的泛化描述。

正常服务修改前的只读核查中，两条读取接口的图表差异为 0，房间版本为 15706。本轮没有再次全量解锁、移动或合并用户图形。运行服务处于 Node watch 模式，后端源码更新自动重启，前端已重新构建。
